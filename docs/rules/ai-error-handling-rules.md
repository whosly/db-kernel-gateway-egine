# AI 错误处理规则

本文档定义在本仓库中处理失败时的工作流。它与 `database-protocol-rules.md` 配套：
协议规则说明"协议应当是什么样"，本文档说明"出错时应当怎么处理"。

优先级与协议规则一致：官方协议文档 > 本规则 > 项目设计 > 当前代码。

## 1. 适用范围

出现以下任一情况，都必须按本文档处理：

- 编译失败、测试失败、构建失败。
- 协议行为（帧、握手、认证、命令、结果集、事务状态、错误包）与官方文档不符。
- 用户或评审反馈指出行为不正确。
- 运行期观测到的状态与规则文档冲突。

## 2. 第一步：先分类，再动手

必须先判定失败属于哪一类，并写清判定依据：

| 类别 | 典型信号 | 处理方向 |
|---|---|---|
| 编译 / 类型 | 编译错误、方法不存在 | 修代码或修测试，不得跳过 |
| 测试断言 | 期望值不符 | 先判定"是代码错还是断言错"，禁止直接改断言 |
| 协议实现 | 与官方协议文档不符 | 以官方协议文档为准修实现，并补测试 |
| 规则文档 | 规则自相矛盾或引用了不存在的资产 | 先修规则，再修实现 |
| 观测偏差 | 观测状态与实际不符，但转发正常 | 按"观测可失败"处理，不得阻塞转发 |
| 环境 / 依赖 | JDK 版本、依赖缺失 | 修环境或声明版本，不得改协议代码绕过 |

分类结论必须能回答："我怎么知道根因是这个？"

## 3. 第二步：一次只修一个原因

- 一次修改只允许引入一个原因层面的变更。
- 禁止把"顺手重构"和"顺便修别的 bug"混在同一次修改里。
- 确实存在多个独立原因时，拆成多次修改，各自单独验证。

## 4. 第三步：必须真实验证

- 声称修好之前，必须实际运行验证命令，并给出真实输出。
- 协议相关改动的最低验证门槛是 `mvn clean test` 全绿。
- 禁止用"看起来没问题""逻辑上应该对"替代验证。
- 禁止为了让测试通过而放宽规则、删除断言、跳过用例或加 `@Disabled`。

## 5. 第四步：禁止掩盖失败

明令禁止：

- 用空 `catch` 或宽泛的 `catch (Exception)` 吞掉失败。
- 用 `printStackTrace()` 代替日志与错误处理。
- 让观测异常冒泡到字节转发路径。
- 把未实现的协议能力伪装成成功响应。
- 把不支持的协议映射到其他协议适配器。
- 为了消除告警而删除有意义的状态或校验。

## 6. 观测与改写的失败策略

- 观测、审计、状态推断失败：**fail-open**。只降级观测结果与置信度，绝不影响转发
  与连接可用性。
- 改写、脱敏失败：**fail-closed**。必须拒绝并返回协议原生错误，绝不"原样放行"，
  也绝不输出部分改写的结果。
- 观测一旦不确定，必须把该会话标记为不可信，并停止基于它做路由、池化或安全决策；
  在协议再同步点（MySQL 客户端命令包 `sequence_id == 0`；PostgreSQL
  `ReadyForQuery`）之后再恢复。

## 7. 第五步：必须回写规则与测试

一次修复只有在下面两项都完成时才算结束：

1. 补上能复现该问题的测试。优先单元测试；需要真实数据库的归入集成测试。
2. 如果该问题暴露的是"流程缺口"而不是一次性笔误，同步更新规则文档或本文档，
   让同类问题下次不再发生。

## 8. 快速自检清单

下面这些做法属于"假修复"，禁止出现：

- 改断言去匹配错误实现。
- 放宽协议校验以让畸形流量通过。
- 删除规则文档中被实现违反的条款。
- 在没有往返测试的前提下开启序列化或改写。
- 观测层遇到不确定时"继续猜"，而不是进入 `SUSPENDED` 并等待再同步点。
